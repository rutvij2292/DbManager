# Tabnix — project log

A personal-use, macOS-first, TablePlus-style database client in Rust (Tauri v2 + TypeScript/Tailwind).

## 2026-10-14
- Project named **Tabnix**. Architecture reviewed by Fable (async-trait `Driver`/`Connection`, paged results kept in Rust, workspace of per-driver crates).
- `rea-agents` evaluated and not used: TablePlus is a native app (not Electron), and I'm not decompiling it. Behavior and shortcuts are recreated from the public UI and docs; all code is original.
- Step 1: workspace, `dbcore`, `driver-sqlite` (with test).
- Feature survey of installed TablePlus (bundle metadata only, no code copied): drivers = SQLite, LibSQL, Cloudflare D1, DuckDB, PostgreSQL, CockroachDB, Greenplum, Redshift, Vertica, MySQL, MariaDB, MSSQL, Oracle, BigQuery, Snowflake, ClickHouse, MongoDB, Redis, Cassandra, DynamoDB, ElasticSearch. Windows/features: connection groups, SSH tunnel, table structure, filter rules, ER diagram, backup/restore, export, command log, AI chat. Roadmap follows this list.
- Step 2: Tauri v2 shell (`src-tauri`) + Vite/TS/Tailwind UI (`ui`). Unlimited tabs (no cap), CodeMirror 6 editor, virtualized grid that pages rows from Rust (`run_query` + `get_rows`, 200k row cap), object sidebar, ⌘P quick open.
- Shortcuts so far: ⌘T new tab, ⌘W close, ⌘1–9 select tab, ⌘⇧[ / ⌘⇧] prev/next, ⌘Enter run (selection or all), ⌘R reload, ⌘P open quickly, ⌘O / ⌘N connections, ⌘L focus search, ⌘I format SQL.
- Step 3: drivers `driver-postgres` (also CockroachDB/Redshift/Greenplum), `driver-mysql` (also MariaDB). Connection manager UI with saved profiles (JSON in app config dir, passwords in macOS Keychain), Test/Save/Connect. Schema-aware autocomplete per dialect via `schema_map`.
- Known gaps: no TLS for Postgres (NoTls) or SSH tunnel yet; no cancel; results are read-only; UI not visually verified (no screen-capture permission in this session); only the SQLite driver has a test.
- Next: row editing with generated SQL preview, EXPLAIN visualization + lint-based optimizer, visual query builder, TLS/SSH, MSSQL/Redis/Mongo.
- Step 4: DataGrip-inspired completion (`ui/src/complete.ts`): tables after FROM/JOIN/INTO/UPDATE, `alias.` → columns, columns from tables in the statement for SELECT/WHERE/GROUP/ORDER (alias-qualified when several tables), suggested JOIN ON conditions (same-name / `<table>_id` → `id`), functions, keywords, snippets (`sel`, `selc`, `ins`, `upd`, `del`, `grp`), usage-based ranking persisted in localStorage.
- Memory goal (light footprint): release profile (opt-level s, LTO, strip, panic=abort), Tokio capped to 2 workers, `sql-formatter` lazy-loaded, rows paged from Rust and released on tab close, schema map holds names only. Release .app = 8 MB. Idle RSS of main process ≈ 97 MB (`ps`, one run, idle with connection dialog open); WebKit helper processes are separate and not isolated in this measurement — needs a proper profile.
- Step 5: query optimizer + plan visualization. `Connection::explain` returns a dialect-neutral `PlanNode` tree: SQLite (`EXPLAIN QUERY PLAN`, tested), Postgres (`EXPLAIN (FORMAT JSON)`, `ANALYZE` with ⌘⇧E), MySQL (tabular EXPLAIN as a flat chain). UI: ⌘E shows the plan tree (bars = share of time/cost/rows) plus suggestions; `ui/src/lint.ts` has static SQL rules (UPDATE/DELETE without WHERE, SELECT *, leading-wildcard LIKE, function on column, NOT IN subquery, cross join, big OFFSET, ORDER BY without LIMIT, DISTINCT+JOIN, OR across columns, correlated subquery) and plan rules (large full scans, estimate-vs-actual mismatch, temp sort). Postgres/MySQL explain paths are untested against live servers.
- Step 6: row editing in table tabs. Double-click a cell to edit (type `NULL` for null), ⌘I / "+ Row" insert, ⌘⌫ / "− Row" mark delete, ⌘S review & commit. Edits are staged client-side (amber = edited, green = new, red = deleted); `dbcore::build_dml` generates dialect SQL shown in a review dialog, then `execute_batch` runs it in one transaction and rolls back if any UPDATE/DELETE doesn't affect exactly one row (tested on SQLite). Tables/views without a primary key are read-only. MySQL uses a real transaction on one connection and backslash-aware literals. UI flow not exercised in a running app (no screen access).
- Step 7: macOS installer. `scripts/build-dmg.sh` builds a universal (arm64 + x86_64) `Tabnix_0.1.0_universal.dmg` (7.3 MB, verified valid, contains Tabnix.app + Applications link). Needs `CI=true` so the bundler skips Finder scripting. App is ad-hoc signed only (no Developer ID / notarization), so Gatekeeper will block the first launch: right-click → Open, or `xattr -dr com.apple.quarantine /Applications/Tabnix.app`.
- Step 8 (v0.2.0): TLS + SSH tunnels. Postgres uses native-tls (macOS Security framework; modes prefer/off/require/verify; `prefer` falls back to plain when the server has no TLS — verified). MySQL uses rustls via mysql_async (off/require/verify; `prefer` = off since there is no cheap fallback). SSH: spawns the system `ssh -N -L` (keys/agent, BatchMode — no password prompts), picks a free local port, waits for it, kills the process on disconnect (`kill_on_drop`). Connection form got SSL + "Connect over SSH" fields. Version bumped 0.1.0 → 0.2.0 (tauri.conf.json, src-tauri, ui).
- Live tests: `crates/driver-{postgres,mysql}/tests/live.rs` (`#[ignore]`; run with `TABNIX_PG_PORT=… / TABNIX_MYSQL_PORT=…`, e.g. against throwaway Docker postgres:16 / mysql:8.0). Both pass: types, objects, describe, schema_map, EXPLAIN, atomic edit rollback, quoting, error path. The MySQL run caught a real bug (text protocol returned numbers as text) — fixed by converting on column type.

- Step 9 (v0.3.0): visual query builder (⌘B in a query tab). `ui/src/builder-sql.ts` is the pure model→SQL generator (joins with suggested ON, per-column aggregates with automatic GROUP BY, AND/OR filters incl. IN / IS NULL / LIKE, DISTINCT, COUNT(*), order, limit; dialect quoting, schema qualification); `ui/src/builder.ts` is the panel that rewrites the editor on every change. `npm test` (in `ui/`) runs 4 node tests on the generator. - Step 10 (v0.4.0): query cancel. `Connection::cancel`: SQLite `interrupt()`, Postgres cancel token (reuses the TLS connector when used), MySQL `KILL QUERY` on a side connection. UI: ⌘. or Esc while running; a tab won't start a second query while one runs. Tested: SQLite unit test, Postgres + MySQL live tests (pg_sleep / SLEEP aborted in < 10 s, connection still usable).

- Step 12 (v0.6.0): **fast import/export** (new `crates/dataio`). Export streams the query result straight from the database to a file in 5000-row batches — constant memory, no 200k UI cap, no trip through the webview — as CSV, TSV, JSON, JSON Lines or executable SQL INSERTs (500 rows/statement, dialect quoting). Streaming is native per driver (`Connection::query_batches`): SQLite stepped reader on a blocking thread, MySQL row stream, Postgres server-side cursor on a private connection (so other tabs' queries are never pulled into its transaction); others fall back to buffering. Import reads CSV/TSV (delimiter sniffed) incrementally with the `csv` crate, or JSON/JSONL; previews the file, maps columns (auto-matched by name, skippable), optionally creates the table with types inferred over the *whole* file (leading zeros stay text), and inserts 500 rows/statement, 20 statements/transaction; an error reports how many rows were already committed. Progress events + cancel (cancelled export deletes its partial file). UI: Import/Export buttons, ⌘⌥E / ⌘⌥I. Measured: SQLite 100k rows export 106 ms / import 534 ms (debug build); live Postgres 50k rows 212 ms / 616 ms, MySQL 196 ms / 927 ms. Tests: 7 dataio tests on SQLite (round trips, quoting, NULL/empty, JSON/JSONL/SQL, mapping, headerless, failure + cancel, 100k speed) + live pg/mysql round trips (`crates/dataio/tests/live.rs`).
- Not done in import/export: Postgres `COPY` / MySQL `LOAD DATA` fast paths (current path is multi-row INSERT in transactions), Excel/XLSX, gzip, importing into Redis/Mongo, and an all-or-nothing option for huge files. The UI dialogs have not been exercised in the running app.

- Step 16 (v0.9.1): **new logo + backup & restore.**
  - Logo: original mark (`assets/logo/`): an "L" threaded through a 3x3 tabnix of nodes on an ultramarine tile, the corner node amber (same amber as primary keys in the app). `tabnix-icon.svg` is the full macOS icon, `tabnix-logo.svg` the flat tile used in the app (home screen, favicon). Rendered with rsvg-convert and checked at 1024/128/64/32 px on light and dark; `tauri icon` regenerated `src-tauri/icons/*` (icns, ico, png sets).
  - **Backup** (`crates/dbbackup`): no pg_dump/mysqldump needed. Writes a plain SQL script (optionally gzip): session prelude, schemas + enum types, `CREATE TABLE`s, data, then indexes / foreign keys / sequence ownership, views, then sequence realignment. Data is `COPY … FROM stdin` blocks on Postgres and size-bounded multi-row INSERTs on MySQL/SQLite; streamed in batches so memory stays flat. Options: pick tables, structure / data / views, compress, add `DROP TABLE IF EXISTS`. Drivers implement `table_ddl` (SQLite: sqlite_master; MySQL: SHOW CREATE TABLE; Postgres: rebuilt from the catalogs — columns via format_type, defaults, identity, generated columns, constraints, indexes, FKs), `view_ddls`, `dump_types`, prelude/epilogue and `sequence_resets`. Cancelling or failing deletes the partial file. SQL Server, Redis and MongoDB are not supported yet and say so.
  - **Restore**: streaming script reader (`script.rs`) that respects quotes, comments, MySQL `DELIMITER`, `/*! */` conditional comments, Postgres `$tag$` bodies and `COPY … FROM stdin` data blocks, and SQLite `CREATE TRIGGER … BEGIN … END`; runs on one session (MySQL needs this for `SET FOREIGN_KEY_CHECKS`); gzip detected by magic bytes; stops at the first error and names the statement, or "keep going" collects the first 20 errors; progress by bytes; cancel. The restore dialog warns (and for production requires an explicit acknowledgement). UI: Backup / Restore buttons in the title bar, ⌘⌥B / ⌘⌥R.
  - Tests: 8 script-reader unit tests; 4 SQLite round trips (plain + gzip, FK/index/trigger/view, awkward text, blob, partial/structure-only/data-only, error handling, cancel removes the file, 100k rows backup 235 ms / restore 347 ms); live MySQL 9.2 (ENUM, FK cascade, AUTO_INCREMENT resumes, view, DELIMITER procedure script); live PostgreSQL 18.6 (enum, serial, identity, generated column, non-public schema, FK cascade, partial index, view, COPY, sequences resume). Both live servers were throwaway and are deleted (Postgres binary checksum-verified, run from the scratch folder).
  - Bugs the tests caught on the way: newlines inside string literals were doubled by the script reader (silent data corruption on restore); `--` comments fused neighbouring tokens; SQLite triggers were split at the first inner `;`; gzip finish panicked (`try_finish` + `flush`); Postgres `pg_get_serial_sequence` was given a quoted column name.

- Step 20: **memory profiling harness** (`scripts/memprofile.sh`, `scripts/memfixture.sh`). Measures `footprint` phys_footprint (Activity Monitor's number, not `ps` RSS) of the main process plus the WebKit helpers it spawned (they are re-parented to launchd, so they are found by diffing helper PIDs before/after launch; the script warns if it doesn't find exactly 3). Scenarios run against a deterministic SQLite fixture (`bench/mem.db`: 100 small tables + a 200k-row `big`, built with the `sqlite3` CLI): cold, connected, large (200k rows scrolled), tabs20, after_close. The app drives itself: `TABNIX_PROFILE=<scenario>` is read by a Rust command that exists only with the `profile` cargo feature, and `ui/src/profile.ts` is only bundled when the UI is built with `VITE_PROFILE=1` (verified: the normal `npm run build` output contains none of it). It builds into `target/profile/` so shipped artifacts are untouched. `--update` stores `bench/mem-baseline.json`; `--check` fails on > 10% and > 15 MB regression per scenario (bench/ is gitignored, so the baseline is local).
- **Baseline (release build, one run, macOS, MB total = main + WebKit):** cold 114.9 (main 26 / webkit 89), connected 118.2, **large 605.5 (main 107 / webkit 499)**, tabs20 152.7, after_close 159.7 (main back to 27.5 from a 122 peak). Findings: (1) the Rust side is small (26 MB idle; the earlier ~97 MB "idle RSS" figure was RSS, not footprint); (2) WebKit is ~3/4 of idle RAM and is the real cost; (3) a 200k-row result costs ~490 MB in the WebView and ~80 MB in Rust, so the grid/row paging is the first thing to attack; (4) memory is returned after closing tabs. Run-to-run noise: a second `cold` run once read 136 MB webkit (a stray helper attributed), so treat < ~15 MB differences as noise.
- Gotcha found: a backgrounded WKWebView throttles `setTimeout` to ~1/s, so scenario code must not loop on timers.
- Step 21 (RAM, step 1 of the 200k-row WebView cost): **bounded result-page cache.** `Grid.cache` kept every 200-row page ever loaded; it is now `PageCache` (`ui/src/pagecache.ts`, LRU, 12 pages ≈ 2,400 rows) and pages holding staged edits/deletes are pinned so a commit can still find its original rows. 4 node tests (limit, recency, pinning, miss). `get_rows` is now an `async` Tauri command (was a sync command, which ran on the app's main thread). Harness: scenarios `large_view` (query only) and `large` (first 12k rows scrolled page by page; `Grid.idle()` waits for pages; a page slower than 2 s is skipped and counted), launched through `open` so the app is foreground.
- **Honest result:** at 60 pages the unbounded cache and the 12-page cache measure the same (WebKit 134 vs 130 MB, both ~30 MB over the 103 MB of `large_view`). The JS heap is not shrunk by WebKit between GCs, so footprint tracks *churn* (each page is ~0.5 MB of parsed `{t,v}` objects), not just what is retained. The bound is verified by unit tests and by the logged cache size (stays at 12), but the footprint win will only show at scale. Biggest remaining costs: ~0.5 MB of JS objects per 200 rows from the `{t,v}` wire format, ~80 MB in Rust for 200k rows (`Vec<Vec<Value>>`), and ~90 MB of WebKit at idle.

Not diagnosed; may be specific to the synthetic scroll loop. Needs a separate investigation before the harness can scroll a full 200k-row result.
