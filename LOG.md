# Lattice — project log

A personal-use, macOS-first, TablePlus-style database client in Rust (Tauri v2 + TypeScript/Tailwind).

## 2026-10-14
- Project named **Lattice**. Architecture reviewed by Fable (async-trait `Driver`/`Connection`, paged results kept in Rust, workspace of per-driver crates).
- `rea-agents` evaluated and not used: TablePlus is a native app (not Electron), and I'm not decompiling it. Behavior and shortcuts are recreated from the public UI and docs; all code is original.
- Step 1: workspace, `dbcore`, `driver-sqlite` (with test).
- Feature survey of installed TablePlus (bundle metadata only, no code copied): drivers = SQLite, LibSQL, Cloudflare D1, DuckDB, PostgreSQL, CockroachDB, Greenplum, Redshift, Vertica, MySQL, MariaDB, MSSQL, Oracle, BigQuery, Snowflake, ClickHouse, MongoDB, Redis, Cassandra, DynamoDB, ElasticSearch. Windows/features: connection groups, SSH tunnel, table structure, filter rules, ER diagram, backup/restore, export, command log, AI chat. Roadmap follows this list.
- Step 2: Tauri v2 shell (`src-tauri`) + Vite/TS/Tailwind UI (`ui`). Unlimited tabs (no cap), CodeMirror 6 editor, virtualized grid that pages rows from Rust (`run_query` + `get_rows`, 200k row cap), object sidebar, ⌘P quick open.
- Shortcuts so far: ⌘T new tab, ⌘W close, ⌘1–9 select tab, ⌘⇧[ / ⌘⇧] prev/next, ⌘Enter run (selection or all), ⌘R reload, ⌘P open quickly, ⌘O / ⌘N connections, ⌘L focus search, ⌘I format SQL.
- Step 3: drivers `driver-postgres` (also CockroachDB/Redshift/Greenplum), `driver-mysql` (also MariaDB). Connection manager UI with saved profiles (JSON in app config dir, passwords in macOS Keychain), Test/Save/Connect. Schema-aware autocomplete per dialect via `schema_map`.
- Known gaps: no TLS for Postgres (NoTls) or SSH tunnel yet; no cancel; results are read-only; UI not visually verified (no screen-capture permission in this session); only the SQLite driver has a test.
- Next: row editing with generated SQL preview, EXPLAIN visualization + lint-based optimizer, visual query builder, TLS/SSH, MSSQL/Redis/Mongo.
- Step 4: DataGrip-inspired completion (`ui/src/complete.ts`): tables after FROM/JOIN/INTO/UPDATE, `alias.` → columns, columns from tables in the statement for SELECT/WHERE/GROUP/ORDER (alias-qualified when several tables), suggested JOIN ON conditions (same-name / `<table>_id` → `id`), functions, keywords, snippets (`sel`, `selc`, `ins`, `upd`, `del`, `grp`), usage-based ranking persisted in localStorage.
- Memory goal (light footprint): release profile (opt-level s, LTO, strip, panic=abort), Tokio capped to 2 workers, `sql-formatter` lazy-loaded, rows paged from Rust and released on tab close, schema map holds names only. Release .app = 8 MB. Idle RSS of main process ≈ 97 MB (`ps`, one run, idle with connection dialog open); WebKit helper processes are separate and not isolated in this measurement — needs a proper profile.
- Step 5: query optimizer + plan visualization. `Connection::explain` returns a dialect-neutral `PlanNode` tree: SQLite (`EXPLAIN QUERY PLAN`, tested), Postgres (`EXPLAIN (FORMAT JSON)`, `ANALYZE` with ⌘⇧E), MySQL (tabular EXPLAIN as a flat chain). UI: ⌘E shows the plan tree (bars = share of time/cost/rows) plus suggestions; `ui/src/lint.ts` has static SQL rules (UPDATE/DELETE without WHERE, SELECT *, leading-wildcard LIKE, function on column, NOT IN subquery, cross join, big OFFSET, ORDER BY without LIMIT, DISTINCT+JOIN, OR across columns, correlated subquery) and plan rules (large full scans, estimate-vs-actual mismatch, temp sort). Postgres/MySQL explain paths are untested against live servers.
- Step 6: row editing in table tabs. Double-click a cell to edit (type `NULL` for null), ⌘I / "+ Row" insert, ⌘⌫ / "− Row" mark delete, ⌘S review & commit. Edits are staged client-side (amber = edited, green = new, red = deleted); `dbcore::build_dml` generates dialect SQL shown in a review dialog, then `execute_batch` runs it in one transaction and rolls back if any UPDATE/DELETE doesn't affect exactly one row (tested on SQLite). Tables/views without a primary key are read-only. MySQL uses a real transaction on one connection and backslash-aware literals. UI flow not exercised in a running app (no screen access).
- Step 7: macOS installer. `scripts/build-dmg.sh` builds a universal (arm64 + x86_64) `Lattice_0.1.0_universal.dmg` (7.3 MB, verified valid, contains Lattice.app + Applications link). Needs `CI=true` so the bundler skips Finder scripting. App is ad-hoc signed only (no Developer ID / notarization), so Gatekeeper will block the first launch: right-click → Open, or `xattr -dr com.apple.quarantine /Applications/Lattice.app`.
- Step 8 (v0.2.0): TLS + SSH tunnels. Postgres uses native-tls (macOS Security framework; modes prefer/off/require/verify; `prefer` falls back to plain when the server has no TLS — verified). MySQL uses rustls via mysql_async (off/require/verify; `prefer` = off since there is no cheap fallback). SSH: spawns the system `ssh -N -L` (keys/agent, BatchMode — no password prompts), picks a free local port, waits for it, kills the process on disconnect (`kill_on_drop`). Connection form got SSL + "Connect over SSH" fields. Version bumped 0.1.0 → 0.2.0 (tauri.conf.json, src-tauri, ui).
- Live tests: `crates/driver-{postgres,mysql}/tests/live.rs` (`#[ignore]`; run with `LATTICE_PG_PORT=… / LATTICE_MYSQL_PORT=…`, e.g. against throwaway Docker postgres:16 / mysql:8.0). Both pass: types, objects, describe, schema_map, EXPLAIN, atomic edit rollback, quoting, error path. The MySQL run caught a real bug (text protocol returned numbers as text) — fixed by converting on column type.
- Still untested: SSH tunnel (needs an sshd), TLS handshake with `require`/`verify` against a TLS server, and all UI flows in the running app.
- Step 9 (v0.3.0): visual query builder (⌘B in a query tab). `ui/src/builder-sql.ts` is the pure model→SQL generator (joins with suggested ON, per-column aggregates with automatic GROUP BY, AND/OR filters incl. IN / IS NULL / LIKE, DISTINCT, COUNT(*), order, limit; dialect quoting, schema qualification); `ui/src/builder.ts` is the panel that rewrites the editor on every change. `npm test` (in `ui/`) runs 4 node tests on the generator. One-way only: SQL → builder is not parsed; self-joins need manual SQL.
- Step 10 (v0.4.0): query cancel. `Connection::cancel`: SQLite `interrupt()`, Postgres cancel token (reuses the TLS connector when used), MySQL `KILL QUERY` on a side connection. UI: ⌘. or Esc while running; a tab won't start a second query while one runs. Cancel is per connection, not per tab (the protocols can't target a single query on a shared connection), so cancelling in one tab can abort a query in another tab on the same connection. Tested: SQLite unit test, Postgres + MySQL live tests (pg_sleep / SLEEP aborted in < 10 s, connection still usable).
- Step 11 (v0.5.0): more engines. **MSSQL** (`driver-mssql`, tiberius/TDS: `[ident]` quoting, `SELECT TOP`, `BEGIN TRANSACTION`, INFORMATION_SCHEMA catalog; builder emits TOP) — compiles and is wired in, **not tested against a server** (the SQL Server image would not pull: Docker VM disk full; I did not prune your Docker data). **Redis** (`driver-redis`): raw commands in the editor, keys as sidebar objects, `@view <key>` renders by type (string/list/set/zset/hash); live test passes against redis:7. **MongoDB** (`driver-mongo`): read-only shell-style commands `db["c"].find({...}).limit(n)`, `.count`, `.aggregate([...])`; fields inferred by sampling; unit test for the parser passes — **live test written but not run** (mongo image would not pull, same disk issue). Non-SQL stores are read-only in the grid (no primary key) and have no EXPLAIN/builder.
- To run live tests: free Docker disk, then `LATTICE_MONGO_PORT=… cargo test -p driver-mongo -- --ignored` (and the same pattern for pg/mysql/redis).
- Step 12 (v0.6.0): **fast import/export** (new `crates/dataio`). Export streams the query result straight from the database to a file in 5000-row batches — constant memory, no 200k UI cap, no trip through the webview — as CSV, TSV, JSON, JSON Lines or executable SQL INSERTs (500 rows/statement, dialect quoting). Streaming is native per driver (`Connection::query_batches`): SQLite stepped reader on a blocking thread, MySQL row stream, Postgres server-side cursor on a private connection (so other tabs' queries are never pulled into its transaction); others fall back to buffering. Import reads CSV/TSV (delimiter sniffed) incrementally with the `csv` crate, or JSON/JSONL; previews the file, maps columns (auto-matched by name, skippable), optionally creates the table with types inferred over the *whole* file (leading zeros stay text), and inserts 500 rows/statement, 20 statements/transaction; an error reports how many rows were already committed. Progress events + cancel (cancelled export deletes its partial file). UI: Import/Export buttons, ⌘⌥E / ⌘⌥I. Measured: SQLite 100k rows export 106 ms / import 534 ms (debug build); live Postgres 50k rows 212 ms / 616 ms, MySQL 196 ms / 927 ms. Tests: 7 dataio tests on SQLite (round trips, quoting, NULL/empty, JSON/JSONL/SQL, mapping, headerless, failure + cancel, 100k speed) + live pg/mysql round trips (`crates/dataio/tests/live.rs`).
- Not done in import/export: Postgres `COPY` / MySQL `LOAD DATA` fast paths (current path is multi-row INSERT in transactions), Excel/XLSX, gzip, importing into Redis/Mongo, and an all-or-nothing option for huge files. The UI dialogs have not been exercised in the running app.
- Remaining roadmap order: table structure editor, ER diagrams, backup/restore (SQL dump), connection groups.
- Benchmark (release, SQLite file, 1,000,000 rows × 7 cols, single run): export CSV 0.69 s (1.44M rows/s), JSON 1.12 s, SQL 1.19 s; import CSV into a new table 4.26 s (234k rows/s). Reproduce: `cargo run --release -p dataio --example bench -- bench/bench.db 1000000` (leaves `bench/bench.db` + `bench.csv` for timing other tools on identical data). No TablePlus numbers: not measurable from this session. Known weak spot: import uses batched INSERTs, not COPY/LOAD DATA.
- Step 13 (v0.7.0): **table structure editor**. Table tabs got a Data / Structure toggle. Structure view edits columns (rename, type, nullable, default, add, drop), indexes (create / drop) and shows foreign keys + DDL; edits are staged, `diffColumns` turns them into `StructChange`s, `dbcore::build_ddl` generates dialect DDL (Postgres `ALTER COLUMN … TYPE … USING`, MySQL `MODIFY COLUMN`, SQL Server `sp_rename`/`ALTER COLUMN`, SQLite add/rename/drop only — it refuses to alter an existing column and says why), the DDL is shown for review, then executed. `ObjectInfo` now also carries `index_details` and `foreign_keys` (SQLite/Postgres/MySQL; reused by the ER diagram). Tests: 3 DDL generator unit tests (all dialects), SQLite metadata + DDL round trip, 4 `diffColumns` UI tests, live Postgres + MySQL structure tests (index columns, composite FK, add/rename/retype/NOT NULL/default/index create+drop) — all pass. MySQL DDL auto-commits, so a failure midway can leave earlier statements applied.
- New requests logged: import connections from TablePlus; light theme + a much better-looking UI (current dark UI judged plain). Both scheduled before ER diagrams / backup / groups.
- Step 14 (v0.8.0): **import connections from TablePlus** (`crates/tableplus-import`). Reads TablePlus' own `Connections.plist` (name, driver, host/port, user, database, SQLite path, Unix socket, SSH host/port/user/key, SSL mode, environment, colour) and maps it to Lattice profiles; the profile id is TablePlus' id so re-importing updates instead of duplicating. Passwords are not in the plist (they're in the Keychain under service `com.tableplus.TablePlus`, account `<id>_database`); an opt-in checkbox reads them via `/usr/bin/security`, which makes macOS ask for permission per item. Unsupported engines (e.g. Snowflake) are listed but disabled. Added Unix-socket support to the MySQL and Postgres drivers (one of the user's TablePlus connections uses a socket). 3 parser tests on synthetic data. The `tLSMode` → SSL mapping (0/1 → default, 2 → require, 3+ → verify) is a guess from observed values and unverified.
- **UI redesign + light theme.** Light is the default, dark is a toggle (⌘⇧L / sidebar button), both driven by CSS tokens (`ui/src/style.css`). IBM Plex Sans + Mono bundled (Latin subsets, ~100 KB). Frosted sidebar with a connection switcher (engine badge + environment stripe), object tree grouped by Tables/Views with counts, document-style tabs, toolbars with icons, a launcher home view listing saved connections (environment stripe, Connect on hover) and a TablePlus import banner. Data grid reworked: row-number gutter, type glyphs in headers, right-aligned tabular numbers, NULL chips, ●/○ booleans, widths by column type. SQL editor now has syntax highlighting (there was none). Structure view, import/export dialogs and modals restyled. Verified visually in a browser through a dev-only mock backend (`?mock` URL, `ui/src/mock.ts`, stripped from production builds) — real screenshots reviewed in light + dark; the packaged Tauri window itself has not been seen.
- **Row filter** (reported missing): table tabs get a Filter bar (⌘F / toolbar button): column / operator / value rules joined by AND/OR (=, <>, <, >, <=, >=, contains, begins with, ends with, in list, is null, is not null) or a raw SQL condition; `select_where` builds the dialect-correct SELECT (TOP for SQL Server); LIKE uses `ESCAPE '!'` so it behaves the same in every dialect. Export respects the active filter. Hidden for Redis/MongoDB. Tests: `buildWhere` UI test, `select_where` unit test; the generated condition was checked at the call boundary in the browser — not yet run against a live MySQL/Postgres.
- Remaining roadmap: ER diagrams, backup/restore (SQL dump), connection groups, Postgres COPY fast path.
- **Bug (reported after TablePlus import): connections opened with no databases.** Cause: TablePlus connections usually leave the database blank and TablePlus then lists every database on the server; Lattice only ever read tables from the one database named in the profile and had no way to list or switch databases (MySQL `DATABASE()` is NULL → empty sidebar). Fix (v0.8.1): `Connection::databases()` (MySQL `SHOW DATABASES`, Postgres `pg_database`, SQL Server `sys.databases`, MongoDB `list_database_names`), `list_databases` / `switch_database` commands (a connection remembers its effective config, incl. any SSH-tunnel rewrite, and reopens against another database under the same id), a searchable database picker (system databases collapsed) that opens automatically when a connection has no database, a sidebar database row, ⌘K, and an explanatory empty state. Postgres now defaults to the `postgres` database instead of one named after the user. Verified: UI flow in the browser mock (light), and a live test against a real MySQL 9.2 server (`live_connection_without_database_lists_and_switches`: lists shop/analytics/system DBs, no tables when none selected, correct tables after reopening each). **Not live-tested:** Postgres/SQL Server/Mongo `databases()` (Docker was down).
- **Import/export performance work (v0.8.1).** Benchmarked 1M rows x 7 cols against native tools (Docker postgres:16 / mysql:8, same data; native numbers include a small `docker exec` pipe overhead). Before: pg export 3.28 s vs native `COPY TO STDOUT` 1.82 s; pg import 16.9 s vs native `COPY FROM` 2.49 s; mysql export 1.45 s vs `mysql --batch` 1.92 s; mysql import 12.1 s vs `LOAD DATA INFILE` 9.14 s. Changes: Postgres `COPY FROM STDIN` bulk path (`Connection::bulk_insert`), Postgres server-side CSV export (`COPY (query) TO STDOUT`, private connection, falls back to the generic writer on error), SQLite prepared-statement bulk path, import now reads 20k-row chunks with byte-sized (<=512 KB) multi-row INSERTs as the fallback. After: pg export 1.49 s, pg import 4.72 s; mysql (a different server — local MySQL 9.2, so not directly comparable to the Docker figures) export 1.37 s, import 7.08 s. TablePlus itself could not be timed from this session (no CLI export, cannot drive its window); protocol for timing it by hand: open the same 1M-row `people` table, export CSV, import into a new table, stopwatch. A first MySQL import attempt failed with "connection closed" at 260k rows — that was Docker/OrbStack dying when the Mac's disk filled (benchmark CSVs + build caches), not a Lattice bug; the rerun on a local mysqld completed.
